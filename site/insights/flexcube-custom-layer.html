The CUSTOM layer: customizing Oracle FLEXCUBE without breaking upgrades

How Oracle FLEXCUBE release layers work, what belongs in the CUSTOM layer, and a checklist for customizations that survive the next upgrade.

Core Banking9 November 20263 min readBy TrustRoute Technologies

Key takeaways

  • FLEXCUBE separates Oracle code (KERNEL) from bank changes (CUSTOM).
  • Customizations made in the CUSTOM layer survive upgrades; edits to KERNEL do not.
  • New fields belong in extension tables, with labels and amendable settings.
  • Check that no Oracle value changes before you load anything.

The most expensive FLEXCUBE customization is not the one that takes longest to build. It is the one that breaks at the next upgrade. Release layers are how you avoid that.

How release layers work

Oracle FLEXCUBE separates what Oracle ships from what a bank adds. Oracle’s own definitions live in the KERNEL layer. Regional or group variations can sit in a CLUSTER layer, and a bank’s own changes belong in the CUSTOM layer. At runtime, the layers combine, so a screen can show Oracle’s fields together with your own.

The rule that keeps upgrades safe is simple: never change KERNEL. When Oracle ships a new release, KERNEL is replaced. Anything edited there is lost or, worse, silently conflicts with the new code.

What belongs in the CUSTOM layer

  • Screen changes in the CUSTOM section of the function’s radxml: new fields, tabs, sections and sub-screens, built in ODT.
  • New data in extension tables linked to Oracle’s tables, rather than new columns on Oracle’s own tables.
  • Back-end logic in the CUSTOM hook package (named for the module and function, ending in _CUSTOM) for validations, defaulting and processing.
  • Front-end logic in the CUSTOM release JavaScript for the function.
  • Labels and static data scripted alongside, so every environment gets the same result.

The details that cause trouble

Most failed customizations fail on small things. New fields that are not marked as amendable cannot be changed on Modify, and FLEXCUBE reports an amendment error. Lists of values with poorly bound queries slow screens on large tables. Labels missing from one environment make a screen look broken in UAT. The TrustForge guides cover several of these in depth, including fixing ST-AMND-002 on Modify and adding a field in the CUSTOM layer.

A checklist before you load

  1. Every new element is tagged to the CUSTOM layer and your release.
  2. No Oracle (KERNEL) value has changed. Compare before and after.
  3. New fields have their data source, block field, field set, labels and amendable settings.
  4. Hook code only extends Oracle logic; it skips or replaces it only where that is the agreed design.
  5. No passwords or keys appear in any file.
  6. Deploy order and unit tests are written down, and the change is tested in your own environments.
